# Idempotency — vì sao nút "Nạp tiền" bấm hai lần không trừ hai lần

> Đây là bài toán mà **mọi** API thanh toán thật đều phải giải, và gần như không dự án học nào
> chạm tới. Stripe, PayPal, Adyen đều dùng đúng cơ chế này.

---

## 1. Vấn đề

Client gửi `POST /wallet/deposits`. Mạng chập chờn. Client **không biết** request đã tới server hay
chưa.

| Client thấy | Thực tế có thể là |
|---|---|
| Timeout | Server chưa nhận → **nên** thử lại |
| Timeout | Server đã xử lý xong, chỉ response bị mất → **không được** thử lại |

Client không phân biệt được hai trường hợp. Mà không thử lại thì mất giao dịch, thử lại thì có nguy
cơ trừ tiền hai lần.

Người dùng bấm đúp nút "Nạp tiền" cũng tạo ra đúng tình huống này.

**Lời giải:** client tự sinh một mã định danh cho **ý định** của mình, gửi kèm mỗi lần thử. Server
đảm bảo một mã chỉ được thực hiện đúng một lần.

```
POST /api/v1/wallet/deposits
Idempotency-Key: 3f7a9c2e-8b1d-4e5a-9c3f-1a2b3c4d5e6f
{"amount": "50.0000"}
```

Gửi lại **cùng key** ⇒ nhận lại **cùng kết quả**, tiền chỉ trừ một lần.

> Điểm mấu chốt: key do **client** sinh, không phải server. Vì key phải tồn tại **trước** khi
> request đầu tiên được gửi — nếu server sinh thì client đã mất nó khi timeout rồi.

## 2. Quyết định lớn nhất: PostgreSQL, không phải Redis

Phản xạ thông thường: "khoá idempotency → Redis, nó nhanh". Dự án này **cố tình không**.

Lý do nằm ở một câu:

> **Khoá idempotency và bút toán sổ cái phải commit nguyên tử.**

Redis và PostgreSQL **không có commit chung**. Nên luôn có một khe hở:

| Thứ tự | Nếu hỏng ở giữa |
|---|---|
| Ghi Redis trước, rồi ghi DB | Redis nói "đã xử lý", DB chưa có gì → **request bị nuốt mất** |
| Ghi DB trước, rồi ghi Redis | DB đã trừ tiền, Redis chưa biết → lần thử lại **trừ tiền lần hai** |

Không có thứ tự nào an toàn. Đó là **two-phase commit problem**, và giải nó đúng cần một
transaction manager phân tán — quá phức tạp so với việc chỉ cần đặt khoá vào cùng cái database.

Đặt khoá trong PostgreSQL thì cả hai nằm trong **một transaction, một COMMIT**:

```java
@Transactional
public TransactionView claimAndRun(...) {
    records.saveAndFlush(new IdempotencyRecord(...));   // khoá
    TransactionView view = action.get();                // bút toán
    record.complete(...);
    return view;                                        // ← một COMMIT cho cả hai
}
```

Cùng sống, cùng chết. Không có trạng thái ở giữa.

**Đánh đổi đã chấp nhận:** chậm hơn Redis. Nhưng đường tiền không tối ưu cho tốc độ trước khi đúng.

## 3. Schema

[`V4__idempotency_and_audit.sql`](../../backend/src/main/resources/db/migration/V4__idempotency_and_audit.sql):

```sql
CREATE TABLE idempotency_key (
    id              BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id         BIGINT        NOT NULL REFERENCES app_user (id),
    idem_key        VARCHAR(64)   NOT NULL,
    endpoint        VARCHAR(64)   NOT NULL,
    request_hash    VARCHAR(64)   NOT NULL,
    response_status INT           NULL,
    response_body   VARCHAR(4096) NULL,
    created_at      TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT uq_idempotency_user_key UNIQUE (user_id, idem_key)
);
```

Ba điểm đáng chú ý:

**`UNIQUE (user_id, idem_key)` — phạm vi theo từng người dùng.** Hai client khác nhau vô tình chọn
cùng một chuỗi key sẽ **không** va nhau. Nếu chỉ `UNIQUE (idem_key)` thì người dùng A có thể (vô
tình hoặc cố ý) chặn giao dịch của người dùng B.

**`request_hash`** — SHA-256 của body. Dùng để phát hiện *"cùng key nhưng nội dung khác"*, tức là
client đang dùng sai.

**`VARCHAR(4096)` chứ không `TEXT`** cho `response_body`. Lý do rất cụ thể: Hibernate ánh xạ
`String` thành `VARCHAR`, và `ddl-auto: validate` so sánh **kiểu JDBC**. Dùng `TEXT` thì ứng dụng
không khởi động được. Đây là bài học từ [bug #5](NHAT_KY_BUG.md), lần đó là `CHAR(64)`.

## 4. Vì sao phải tách làm hai lớp

Đây là phần tinh tế nhất của cả cơ chế.

**Ràng buộc từ PostgreSQL:** một câu lệnh gây lỗi sẽ **huỷ toàn bộ transaction**. Mọi câu lệnh sau
đó bị từ chối cho tới khi `ROLLBACK`.

Nên khi hai request đua nhau trên cùng một key:

```
Request A: INSERT khoá ✔  (chưa commit)
Request B: INSERT khoá ✘  → vi phạm UNIQUE → transaction của B CHẾT
Request B: muốn đọc dòng của A để trả lại kết quả...  ✘ KHÔNG THỂ, transaction đã chết
```

Và kể cả nếu đọc được, dòng của A **chưa commit** nên ở READ COMMITTED cũng không nhìn thấy.

Vì vậy phải có một lớp **đứng ngoài** transaction đã chết để diễn giải:

| Class | `@Transactional`? | Việc |
|---|---|---|
| [`IdempotencyService`](../../backend/src/main/java/com/walletledger/idempotency/IdempotencyService.java) | **Không** | Đọc trước, diễn giải, quyết định câu trả lời |
| [`IdempotentExecutor`](../../backend/src/main/java/com/walletledger/idempotency/IdempotentExecutor.java) | **Có** | Giành khoá + chạy thao tác, cùng commit |

```java
// IdempotencyService — KHÔNG @Transactional
Optional<IdempotencyRecord> existing = records.findByUserIdAndIdemKey(userId, key);
if (existing.isPresent()) {
    return replay(existing.get(), endpoint, requestHash);
}
try {
    return executor.claimAndRun(userId, key, endpoint, requestHash, action);
} catch (DataIntegrityViolationException e) {
    if (!isKeyCollision(e)) { throw e; }
    throw new IdempotencyInProgressException();   // 409
}
```

### `saveAndFlush`, không phải `save`

```java
records.saveAndFlush(new IdempotencyRecord(userId, key, endpoint, requestHash));
```

`save` chỉ đưa entity vào persistence context; INSERT thật có thể hoãn tới lúc commit. Khi đó lỗi
trùng khoá sẽ nổ **lúc commit** — đã thoát khỏi khối `try` của caller.

`saveAndFlush` ép INSERT chạy **ngay**, nên lỗi nổ đúng chỗ bắt được nó.

## 5. Bốn tình huống và câu trả lời

| Tình huống | Trả về | Vì sao |
|---|---|---|
| Cùng key, cùng request, đã xong | Phát lại response đã lưu | Đúng nghĩa idempotent |
| Cùng key, **khác body hoặc khác endpoint** | `422` | Client đang dùng sai key |
| Cùng key, đồng thời, kẻ thắng chưa commit | `409` | Không thể đọc, và **không được đoán** |
| Thao tác thất bại | Khoá rollback theo, key được giải phóng | Retry sau lỗi tạm thời phải làm được |

### Vì sao 409 chứ không phải chờ rồi trả kết quả của kẻ thắng

Vì response của kẻ thắng **chưa tồn tại**. Đoán nó là bịa. Stripe trả lời tình huống này y hệt: nói
client thử lại sau một chút.

### Vì sao thao tác thất bại KHÔNG được tiêu key

Nếu ghi nhận cả thất bại, client gặp lỗi mạng tạm thời rồi thử lại **sẽ không bao giờ thành công
được nữa** — key đã bị đánh dấu. Mà thử lại chính là việc client sinh ra để làm.

Nhờ khoá và bút toán nằm cùng một transaction, điều này **tự động đúng**: thao tác ném exception ⇒
rollback ⇒ dòng khoá biến mất.

## 6. Lỗ hổng thật: một key dùng lại được ở endpoint khác

Ban đầu `replay()` chỉ so `request_hash`:

```java
if (!record.getRequestHash().equals(requestHash)) {
    throw new IdempotencyKeyReusedException();
}
```

Cột `endpoint` **có** được lưu nhưng **không** được so. Và `deposit` với `withdrawal` **dùng chung**
`AmountRequest`, nên `canonicalise` sinh ra **cùng một chuỗi JSON**.

Probe HTTP thật:

```
POST /wallet/deposits     key=K  {"amount":"10.0000"}  →  201  type=DEPOSIT
POST /wallet/withdrawals  key=K  {"amount":"10.0000"}  →  201  type=DEPOSIT   ← replay!
GET  /wallet                                           →  balance = 10.0000
```

**Lệnh rút không hề xảy ra**, nhưng client nhận mã thành công.

Sửa:

```java
if (!record.getEndpoint().equals(endpoint) || !record.getRequestHash().equals(requestHash)) {
    throw new IdempotencyKeyReusedException();
}
```

> **Bài học:** danh tính của một request **không chỉ là body**. Nếu bạn lưu một trường vào bảng mà
> không bao giờ đọc nó, hãy hỏi tại sao nó ở đó — hoặc nó thừa, hoặc bạn đang quên dùng nó. Ở đây
> là vế thứ hai.

## 7. Lỗ hổng thật: `catch` quá rộng biến lỗi sổ cái thành "thử lại đi"

```java
} catch (DataIntegrityViolationException e) {     // ← bắt MỌI vi phạm toàn vẹn
    throw new IdempotencyInProgressException();   // → 409 "Retry shortly"
}
```

`DataIntegrityViolationException` là lớp cha của **mọi** vi phạm ràng buộc. Nên nếu constraint
trigger `trg_transaction_balanced` từ chối một giao dịch không cân bằng — **lỗi nghiêm trọng nhất
hệ thống có thể gặp** — client sẽ nhận `409 "Request in progress. Retry shortly."` và **thử lại
thật**.

Bằng chứng cụ thể xuất hiện tình cờ, từ bước đỏ của một test khác: gọi `post()` với `amount = 0` bị
`ck_entry_amount_non_zero` chặn ở DB và ném đúng lớp exception đó.

### Và cách sửa "hiển nhiên" thì SAI

Phản xạ: đổi sang `catch (DuplicateKeyException)` — Spring có sẵn lớp con đúng cho trường hợp này.

Viết test khoá lại giả định **trước khi** sửa:

```
duplicate key value violates unique constraint "uq_idempotency_user_key"   (SQLSTATE 23505)
Expecting actual throwable to be an instance of: [DuplicateKeyException]
but was: org.springframework.dao.DataIntegrityViolationException
```

Qua **JPA**, `HibernateJpaDialect` dịch mọi `ConstraintViolationException` của Hibernate thành
`DataIntegrityViolationException` **chung**. `DuplicateKeyException` **chỉ** xuất hiện trên đường
**JdbcTemplate**, nơi `SQLExceptionSubclassTranslator` phân loại theo SQLSTATE.

**Cùng một CSDL, cùng một lỗi, hai lớp exception khác nhau tuỳ đường đi.**

Nếu không có test đó: `catch (DuplicateKeyException)` **biên dịch được**, đọc qua thấy đúng, và
**mọi test cũ vẫn xanh** — vì không test nào chạy hai request đua nhau. Idempotency sẽ hỏng **lặng
lẽ** trên môi trường thật.

Cách sửa đúng — nhận diện bằng **tên constraint**:

```java
private static final String KEY_UNIQUE_CONSTRAINT = "uq_idempotency_user_key";

private boolean isKeyCollision(DataIntegrityViolationException e) {
    return e.getCause() instanceof ConstraintViolationException violation
            && KEY_UNIQUE_CONSTRAINT.equalsIgnoreCase(violation.getConstraintName());
}
```

Chi tiết: [bug #11](NHAT_KY_BUG.md).

for (int i = 0; i < 16; i++) {
    results.add(pool.submit(() -> {
        startGate.await();

## 9. Chỗ chưa làm

- **Không có TTL, không có job dọn.** Bảng `idempotency_key` phình vô hạn. Hệ thống thật đặt TTL
  24–72 giờ. Đây là thiếu sót thật, đã ghi nhận.
- **`response_status` được lưu nhưng replay không dùng.** Hiện replay để controller tự trả 201.
  Đúng về hành vi, nhưng nếu sau này khôi phục mã trạng thái từ DB thì phải cẩn thận.
- **Nhánh "đang xử lý" (`!isComplete()`) không thể tới được** với luồng hiện tại — `claimAndRun`
  điền response body trước khi commit, và READ COMMITTED giấu dòng chưa commit. Nó được giữ lại như
  hàng rào chống `decode(null)`. Comment trong V4 mô tả cơ chế này khác thực tế, nhưng **không được
  sửa file migration đã chạy** — đổi một ký tự là đổi checksum Flyway và app sẽ không khởi động.
- **Chưa giới hạn tần suất.** Người dùng đã xác thực có thể sinh vô hạn key.

## 10. Nếu bị hỏi

**"Idempotency là gì và vì sao cần?"**
Là đảm bảo cùng một request gửi nhiều lần chỉ có tác dụng một lần. Cần vì client không phân biệt
được "server chưa nhận" với "server xử lý xong nhưng response mất" — cả hai đều hiện ra là timeout.
Client sinh một `Idempotency-Key`, gửi kèm mọi lần thử; server đảm bảo một key chỉ thực thi một lần.

**"Vì sao không để khoá trong Redis cho nhanh?"**
Vì khoá và bút toán phải commit nguyên tử. Redis và Postgres không có commit chung, nên ghi Redis
trước thì có thể nuốt mất request, ghi Postgres trước thì lần retry sẽ trừ tiền hai lần. Đặt khoá
vào cùng database biến hai việc thành một transaction, một COMMIT. Em chấp nhận chậm hơn để đổi lấy
tính đúng.

**"Hai request cùng key chạy đồng thời thì sao?"**
`UNIQUE (user_id, idem_key)` quyết định ai thắng. Kẻ thua nhận **409**, không phải response đoán —
vì transaction của kẻ thắng chưa commit nên response của nó chưa tồn tại. Điểm tinh tế là vi phạm
unique **huỷ luôn transaction PostgreSQL**, nên kẻ thua không thể đọc dòng kẻ thắng từ bên trong;
vì vậy em tách thành hai bean, một cái không transactional để diễn giải từ bên ngoài.

**"Em có gặp lỗi gì ở phần này không?"**
Hai cái đáng nhớ. Một key dùng lại được ở endpoint khác, vì `replay()` chỉ so hash của body mà
deposit và withdrawal dùng chung cùng một DTO — em dựng probe HTTP tái hiện được: lệnh rút trả 201
với `type: DEPOSIT` và tiền không hề bị rút. Và khi thu hẹp khối `catch`, em suýt đổi sang
`DuplicateKeyException` — một test viết trước khi sửa cho thấy qua JPA thì lớp đó **không bao giờ**
được ném, nên thay đổi đó sẽ vô hiệu hoá idempotency mà không test nào đỏ.
